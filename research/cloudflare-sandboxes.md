**Date gathered:** 2026-10-11 (`date -u +%Y-%m-%d`).
**Volatility warning:** Cloudflare Sandboxes docs were restructured on **2026-09-30** (several pages updated Sep 30 / Oct 5, 2026), Sandbox SDK 1.0 shipped **2026-09-30** with SDK 0.x on a **2026-12-31 fix-EOL**, and two features flagged in this report (snapshots, the `durable_object` scheduling policy) are **public beta** — numbers and flags below can change quickly; re-verify before relying on them.

## 1. Overview

- A sandbox is "an isolated place to run code. The code cannot directly read the memory or data of your application. Your Worker decides which application APIs and data the code receives, and whether the code can reach the public Internet."
  ([/sandbox/](https://developers.cloudflare.com/sandbox/), page last updated Sep 30, 2026; "Available on Workers Paid plan")
- Stated use cases: "agent-written code, user-uploaded applications, data analysis, development previews, build pipelines, or any other work that should not share a process with your application"; the docs' how-to list also includes running coding agents ("Run coding agents such as Claude Code, Codex, and Devin in a sandbox that belongs to one task"). ([/sandbox/](https://developers.cloudflare.com/sandbox/))
- Cloudflare provides **two sandbox environments**, both accessed through a Worker:
  1. **Containers** — a Firecracker microVM ("full Linux environment … its own kernel and network, so no other workload shares it"), started from a Durable Object in your Worker. Inbound HTTP reaches the instance only through the Worker. This is what `@cloudflare/sandbox` targets. ([/sandbox/](https://developers.cloudflare.com/sandbox/))
  2. **Dynamic Workers** — a new Worker created at runtime for untrusted JavaScript, Python, or WebAssembly (TypeScript must be pre-compiled), with `globalOutbound: null` blocking outbound fetch. ([/sandbox/](https://developers.cloudflare.com/sandbox/), [Run JavaScript](https://developers.cloudflare.com/sandbox/) next-steps)
- The minimal get-started flow: a Worker + Durable Object class with a container binding calls `ctx.container.start({ image: "cloudflare/debian-trixie", entrypoint: ["sleep", "infinity"], enableInternet: false })` and `container.exec(argv)`; `wrangler dev` runs the instance in local Docker (needs Wrangler ≥ 4.141.0). ([/sandbox/get-started/](https://developers.cloudflare.com/sandbox/get-started/), updated Sep 30, 2026)

## 2. Cost

Sandboxes run on Cloudflare Containers; the authoritative pricing is the Containers pricing page (there is no separate Sandbox pricing page — checked [/sandbox/reference/](https://developers.cloudflare.com/sandbox/reference/) and [/sandbox/](https://developers.cloudflare.com/sandbox/), 2026-10-11; the overview page states only "Available on Workers Paid plan").

**Compute, memory, disk — billed per 10 ms of active running time** ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/), updated Oct 5, 2026):

| Plan | Memory | CPU | Disk |
| --- | --- | --- | --- |
| Free ("Free") | N/A | N/A | (blank in table — Containers not offered on free) |
| Workers Paid | **25 GiB-hours/month included** + **$0.0000025 per additional GiB-second** | **375 vCPU-minutes/month included** + **$0.000020 per additional vCPU-second** | **200 GB-hours/month included** + **$0.00000007 per additional GB-second** |

- "Charges start when a request is sent to the container or when it is manually started. Charges stop after the container instance goes to sleep" — i.e. **scale/sleep-to-zero**; billing granularity is per 10 ms ("billed for every 10ms that they are actively running"). ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))
- "Memory and disk usage are based on the provisioned resources for the instance type you select, while **CPU usage is based on active usage only**." ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))
- Included allowances are part of the **$5/month Workers Paid plan** ("included monthly usage as part of the $5 USD per month Workers Paid plan"). ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))
- Instance types drive the bill ("larger instances include more memory and disk … which allows you to incur higher CPU costs"): `lite` (1/16 vCPU, 256 MiB, 2 GB), `basic` (1/4, 1 GiB, 4 GB), `standard-1` (1/2, 4 GiB, 8 GB), `standard-2` (1, 6 GiB, 12 GB), `standard-3` (2, 8 GiB, 16 GB), `standard-4` (4, 12 GiB, 20 GB). ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/) and [/containers/platform/limits/](https://developers.cloudflare.com/containers/platform/limits/), both updated Sep 30, 2026)
- **Network egress** (charged in addition to compute): North America & Europe **$0.025/GB** (1 TB/month included); Oceania, Korea, Taiwan **$0.05/GB** (500 GB included); Everywhere Else **$0.04/GB** (500 GB included). ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))
- Incoming requests hit your Worker and each container has its own Durable Object, so **Workers and Durable Objects are billed separately** on top. ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))
- Container logs are billed at Workers Logs rates. ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/))

## 3. Specifications

**Runtimes/images** ([/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/), updated Sep 30, 2026; [/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/)):

- Each instance is a **Firecracker microVM** with its own kernel and network; the image runs as a Linux container inside it.
- Images must be **`linux/amd64`**; "the container instance is a full Linux environment, so you can run any language" ([/sandbox/](https://developers.cloudflare.com/sandbox/)).
- First-party image: `cloudflare/debian-trixie` ("Debian Trixie with Node.js 24"). ([/sandbox/get-started/](https://developers.cloudflare.com/sandbox/get-started/), [/sandbox/reference/](https://developers.cloudflare.com/sandbox/reference/))
- For the Dynamic Worker environment, untrusted code can be **JavaScript, Python, or WebAssembly** (compile TS first). ([/sandbox/](https://developers.cloudflare.com/sandbox/))

**Instance types and custom-size constraints** ([/containers/platform/limits/](https://developers.cloudflare.com/containers/platform/limits/)): six predefined types (table above); custom types: min vCPU 1, max vCPU 4, max memory 12 GiB, max disk 20 GB, min 3 GiB memory per vCPU. `dev` and `standard` are backward-compat aliases for `lite` and `standard-1`.

**Account limits** ([/containers/platform/limits/](https://developers.cloudflare.com/containers/platform/limits/)): concurrent memory 6 TiB; concurrent vCPU 1,500; concurrent disk 30 TB; image size same as instance disk; total image storage per account 50 GB¹ (superscript footnote on page, not expanded in fetched text).

- **Container-level limits**: image size ≤ instance disk space; **max snapshot size 20 GB**; snapshot retention 30 days from creation or most recent restore (restore refreshes TTL). ([/containers/platform/limits/](https://developers.cloudflare.com/containers/platform/limits/))
- **No separate max-instance count is documented for the `durable_object` scheduling policy** (the `default` policy has a `max_instances` Wrangler setting, [/containers/configuration/scheduling-policy/](https://developers.cloudflare.com/containers/configuration/scheduling-policy/)); the hard ceiling is the account-level aggregate (above).

**Timeouts / sleep** ([/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/), [/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/)):

- `setInactivityTimeout(durationMs)` must be **> 0 and ≤ 6 hours (21,600,000 ms)**; the instance keeps running after the Durable Object goes inactive for that long.
- Platform stop sequence: SIGTERM to main process → wait **up to 15 minutes** → SIGKILL. `destroy()` stops immediately (no cleanup time for processes).
- A pending `monitor()` call keeps it running for up to 15 minutes.
- Cold starts "often in the 1-3 second range" depending on image size and entrypoint. ([/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/))

**Networking / egress**:

- No inbound: "end-users cannot make non-HTTP TCP or UDP requests to a Container instance" — requests come in via the Worker; HTTP(S) per-port forwarding uses `getTcpPort(port)`. ([/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/), [/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/))
- Outbound: containers start with **`enableInternet: false` by default**; only requests intercepted by an outbound handler in your Worker leave. Handlers see HTTP on port 80 and HTTPS on 443; with internet on, other ports go out directly. HTTPS interception **requires trusting the Cloudflare CA cert**. Limits: up to **64 hostname targets or 128 IP/CIDR targets**, and an error "You can't configure more than 128 egress interceptors". ([/sandbox/concepts/security/](https://developers.cloudflare.com/sandbox/concepts/security/), [/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/))
- **Preview URLs / ports**: 0.x SDK docs state "Production requires custom domain — Preview URLs require a custom domain with wildcard DNS routing in production" ([/sandbox/api/ports/](https://developers.cloudflare.com/sandbox/api/ports/), updated Aug 13, 2026); the 1.0 changelog says 1.0 serves "previews from ports in the sandbox, with your own hostnames and authentication". ([/changelog/post/2026-09-30-sandbox-sdk-1-0/](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/))
- **Tunnels**: 0.x exposes services via `sandbox.tunnels` with `cloudflared` inside the sandbox ([announcement changelog, 2026-05-29](https://developers.cloudflare.com/changelog/post/2026-05-29-sandbox-named-tunnels/)); in 1.0, tunnels are covered by the migration guide ("the guide keeps the preview URLs and named tunnels that your 0.x application created working", [/changelog/post/2026-09-30-sandbox-sdk-1-0/](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/)).

**Placement / regions**: containers run "in the location nearest to the incoming request with a pre-fetched image"; "Durable Objects and their associated Container instances are **not guaranteed** to run in the same location"; restarts may land in a different location. **No published list of sandbox/containers regions** (checked [/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/), 2026-10-11 — placement constraints exist for data residency per the placement docs).

**API / integration surface**

- **Durable Object Container API** (`this.ctx.container`, recommended for new apps) — documented methods/properties ([/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/), updated Sep 30, 2026): `images` (read-only, `durable_object` policy), `running`, `start({ image, instance, entrypoint, env, enableInternet, containerSnapshot, labels })` (start returns before ready), `monitor()`, `inspect()`, `exec(cmd, { cwd, env, user, AbortSignal, pty })` → ExecProcess with stdin/stdout/stderr, `pid`, `exitCode`, `output()`, `kill(signal 1–64, default SIGTERM=15)`, `resize(1–65535)`, **no built-in timeout on exec**, `snapshotContainer()` (`durable_object` policy only), `destroy(error?)`, `signal(number)`, `setInactivityTimeout(ms)`, `getTcpPort(port)`, `interceptOutboundHttp(addr, binding)`, `interceptAllOutboundHttp(binding)`, `interceptOutboundHttps(addr, binding)`. Labels: max 10, names 1–16 bytes, values ≤ 64 bytes.
- **`@cloudflare/sandbox` 1.0 package**: "works with a container you start from a Durable Object. Its classes run helper processes in the running container through `exec()`. The package **does not start, stop, or monitor** the container." Exports **`Files`** (streams files in/out), **`S3Mount`** (mounts an S3-compatible bucket such as R2; the Worker signs each storage request "so the credentials stay out of the sandbox"), **`DirectoryBackup`** (saves a directory to R2 and restores into any sandbox, including a newer image). Requirements: helper binary `/usr/local/bin/sandbox-shim` copied from `docker.io/cloudflare/sandbox:<VERSION>` (statically linked linux/amd64), Worker with `nodejs_compat`, container already running. ([/sandbox/reference/](https://developers.cloudflare.com/sandbox/reference/), updated Sep 30, 2026; [1.0 changelog](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/))
- **Terminals & background work**: 1.0 supports "run commands with streamed input and output, send them signals, and open terminals"; inner activity does not count as activity — keep a long task alive with a Durable Object alarm ("Run background processes uses an alarm that runs every minute"). ([/changelog/post/2026-09-30-sandbox-sdk-1-0/](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/), [/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/))
- **Snapshots** = save/restore of the writable root filesystem: `snapshotContainer()` snapshot handle has `id`/`size`/`name`; stored (e.g. in Durable Object storage) and passed to the next `start()` as `containerSnapshot`; "Cloudflare does not restore a snapshot on its own"; does not save `/run`, mounted filesystems, memory, or processes; restored instance re-runs its entrypoint; restored PIDs can be reused by other processes; **public beta**. ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/), [/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/))
- **R2 bucket mounts outlive every instance**; mounting is per-instance. ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/))
- **Code interpreter** (Python/JS/TS with visualizations and contexts) is documented as **SDK 0.x** ([/sandbox/sdk/api/interpreter/](https://developers.cloudflare.com/sandbox/sdk/api/interpreter/), updated Sep 30, 2026); the 1.0 migration guide covers "preview URLs, tunnels, background processes, terminals, backups, and the code interpreter" for 1.0 apps ([/changelog/post/2026-09-30-sandbox-sdk-1-0/](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/)).
- **MCP: not documented** on the Sandboxes docs (checked site search over developers.cloudflare.com/sandbox, 2026-10-11). MCP-related changelog entries found concern MCP portals, a different product.
- **Subrequest limits for the 0.x SDK** (informational, the package this repo uses historically): Workers Free 50 subrequests/request, Paid 1,000; each SDK operation counts as one; `SANDBOX_TRANSPORT=rpc` multiplexes over one persistent connection. ([/sdk/platform/limits/](https://developers.cloudflare.com/sandbox/platform/limits/) → rendered page titled "Limits (Sandbox SDK 0.x)", updated Sep 30, 2026)

## 4. Limitations

- **Security model — one sandbox is one trust boundary**: every process in a container runs on the same Linux system and "every process has the same Linux capabilities as `root`" — file permissions and separate users do not restrict code; anything placed inside (files, env vars, tokens in `.git/config`) is readable by all code in the sandbox, which is why the docs recommend keeping credentials in the Worker via outbound handlers. ([/sandbox/concepts/security/](https://developers.cloudflare.com/sandbox/concepts/security/), updated Sep 30, 2026)
- **Egress is the other side of ingress**: any destination you allow gives the code a way out; each outbound rule is an escape path for anything the sandbox can read. ([/sandbox/concepts/security/](https://developers.cloudflare.com/sandbox/concepts/security/))
- **Sandbox identity is name-based, not authenticated**: the container keeps its files while running and the name routes to the same DO — "Authenticate the caller in your Worker, and derive the sandbox name from that identity. Reusing a name or a snapshot for someone else gives them the earlier user's files." ([/sandbox/concepts/security/](https://developers.cloudflare.com/sandbox/concepts/security/))
- **Lifetime / state**: name + Durable Object persist, the instance does not. Instance stops on: inactivity timeout, `destroy()`, or main process exit. SIGTERM → up to 15 min → SIGKILL. All files/processes/state end when the instance stops unless snapshot- or bucket-backed first. Changes after the last snapshot are only in the current instance. (**Inner activity does not count** — a build/test/agent task running inside does not keep the instance alive; without requests it stops at the timeout.) ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/), [/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/))
- **Inactivity timeout does not survive a DO restart**: after deploy/eviction the restarted DO has no timeout, so "the instance stops shortly after the Durable Object becomes inactive" — set it again in the constructor. Cloudflare does not wake the DO when the instance stops. ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/))
- **Deploys**: restart the DO but **keep running instances**; instances keep the image/entrypoint/env they started with (`start()` throws while running), so image changes apply only on the next start; deploy kills in-flight requests, streamed responses and WebSockets; browser terminal disconnects. For the `durable_object` policy, container rollouts never replace sandboxes. ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/), [/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/))
- **Ephemeral disk by default**: on stop, next start uses a fresh disk from the image; persistence requires snapshot (beta) or mounting R2/FUSE. ([/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/))
- **Free plan**: Containers/sandboxes are effectively Workers Paid only — pricing table shows Free N/A for memory/CPU; overview banner "Available on Workers Paid plan". ([/containers/pricing/](https://developers.cloudflare.com/containers/pricing/), [/sandbox/](https://developers.cloudflare.com/sandbox/))
- **Beta / preview caveats** (flagged on the docs themselves):
  - The **`durable_object` scheduling policy is in public beta** — and every sandbox that uses it inherits that status; policy choice is **immutable per Container application** (switching means replacing every running instance). ([/sandbox/](https://developers.cloudflare.com/sandbox/), [/containers/configuration/scheduling-policy/](https://developers.cloudflare.com/containers/configuration/scheduling-policy/))
  - **Container snapshots are in public beta**; "The API and behavior may change." ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/))
  - **Sandbox SDK 0.x is legacy**: "Sandbox SDK 0.x receives bug and security fixes until **2026-12-31**"; docs moved to the "Sandbox SDK 0.x" section. ([/changelog/post/2026-09-30-sandbox-sdk-1-0/](https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/))
  - Not beta/GA-flagged but notable: the 1.0 docs themselves are one day old as of a late Sept restructure ([/sandbox/](https://developers.cloudflare.com/sandbox/), last updated Sep 30, 2026); some sub-pages still show older "Last updated Aug 7/Aug 13, 2026" dates and pre-1.0 "Coming soon: Sandbox SDK 1.0" banners (e.g. [/sandbox/api/ports/](https://developers.cloudflare.com/sandbox/api/ports/)), and one legacy URL still renders 0.x content under a non-`sdk` path ([/sandbox/platform/limits/](https://developers.cloudflare.com/sandbox/platform/limits/)).
- **Other restrictions**: no inbound raw TCP/UDP from end users; no built-in exec timeout (use AbortSignal); no published region list; `snapshotContainer` only under the `durable_object` policy; no separate Sandbox pricing page (prices live on Containers). ([/containers/concepts/architecture/](https://developers.cloudflare.com/containers/concepts/architecture/), [/containers/api/durable-object-container/](https://developers.cloudflare.com/containers/api/durable-object-container/))

## 6. Relevance footnote — pi-coding-agent

This repo deploys the stable `@cloudflare/sandbox` 1.0 package with `scheduling_policy: durable_object` and a Dockerfile-built image, one `PiSandbox` Durable Object running a coding agent per task. The cost model means: billing runs while the DO is active or within the inactivity window (per-10ms memory-billing on the provisioned instance type; CPU only on active use), so an idle agent between requests scales to zero within ≤ 6 h — but docs warn that **work inside the container does not count as activity** ([/sandbox/concepts/lifetime/](https://developers.cloudflare.com/sandbox/concepts/lifetime/): "even while a build, a test suite, or an agent task still runs"), so long agent tasks must keep the DO busy (alarm per minute) or the bill goes quiet and the box dies mid-task. The 6 TiB / 1,500-vCPU account ceilings cap fleet concurrency; `lite`/`basic` sized sandboxes with sleep-to-zero keep an ephemeral-agent fleet cheap, where a permanently-idling standard-4 instance would burn the included allowances fast and pay ~$0.0876/hour for memory alone (2,880 GiB-hrs × $0.0000025/GB-s ÷ 3600). The repo's Worker-side outbound proxy matches the docs' credentials-outside-the-sandbox model, and the sandbox-name-from-authenticated-identity rule matters here since one task's workspace must not leak to another caller by name. Snapshots (beta, 20 GB / 30-day TTL) are the only built-in way to carry a repo workspace across instance stops; the repo's current pattern loses container files on every stop unless snapshot- or R2-backed. Deploy behavior is favorable for CI-style use: deploys do not restart running agent sandboxes, but new images only apply on the next start.
